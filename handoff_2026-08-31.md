### Ordering — complete, plan archived

Fractional `rank` is gone from the codebase: three columns, six indexes, the
`fractional-indexing` dependency, `lib/ordering.ts`, `lib/documentOrder.ts` and
most of `repositories/ordering.ts`. Order now lives in an array on the container
that owns the list, read through one tolerant reader (`src/lib/orderArray.ts`)

**Four arrays, not the three the plan specified.** `Project` owns its member

`tabOrder` on the post itself.

## Traps learned — worth carrying forward

1. **Prisma generates destructive SQL for column changes.** `DROP` + `ADD` for
   the `role` enum conversion (would have discarded every role) and for both
   phase B and C changes; C's would not even have run. **Three of the four
   schema changes across all four phases.** Hand-write the SQL and rehearse it
   against a restored copy.
2. **`tsc` has blind spots on a field rename.** Four breaks it could not see,
   all 500s on the main read path: two `as const` Prisma selects (validated only
   at query time), a `Record<string, unknown>` cast, and two `$queryRaw`
   templates. `grep -rn 'name: true'` and `grep -rn '\$queryRaw'` found them.
   "Let TypeScript surface the call sites" is necessary, not sufficient.
3. **An IndexedDB upgrade can lose data while looking like it worked.** The
   first `name → title` migration ran one cursor pass per version; three cursors
   on one store each held the record as they found it and took turns writing
   back, last write winning. A real profile came out with one of three renames
   applied *while the index swaps beside it succeeded*. Fixed by folding every
   crossed version into a single pass per store, with the transform exported so
   the spec drives the same function the browser does.
4. **`git status` hides untracked files in this repo**
   (`status.showUntrackedFiles=no`). 46 build-output files rode into `d458483b`
   because a dev server recreated `.next-verify` between the `rm -rf` and the
   commit. Kill the server *before* deleting its build dir, and check with
   `--untracked-files=all`.
5. **`:3000` is usually a stale `next start` production build.** Do not clobber
   it: `next.config.ts` reads `distDir` from `BUILD_DIR`, so
   `BUILD_DIR=.next-verify pnpm dev -p 300X` runs a dev server beside it.
   Afterwards revert `tsconfig.json`, which the dev server edits.
6. **Sidebar multi-select needs the modifier on every click.** Selection is
   `useRowSelection(ids, "clear")`, under which a plain click sets only the
   anchor. A plain-then-ctrl click selects one row and the drag silently carries
   one while looking like it carries two.
7. **`docker compose up -d` would kill the dev database.** `postgres-blog`
   (postgres:17.2) already serves 5432 with the real data; the repo's compose
   file defines a different service on that port.

## Bugs found in passing

- **`/api/import` could never import a new document.** It wrote each document's
  revisions before the row they point at, so the first hit
  `Revision_documentId_fkey` and the whole import failed. Pre-existing, silent,
  untested. Fixed as a side effect of phase B.
- **Creates did not maintain the store's order arrays.** Phase 4 added that for
  re-homes but left creates to the tolerant reader, so a `placement: "start"`
  post read *last* until the next load — invisible for a signed-in user because
  the server prepended and a reload settled it, not invisible for a guest whose
  store *is* the read. Fixed in phase 5.
- **`Document.parentId` would have been left with no index at all.** Its only
  one was the composite with `rank`, and "the children of this post" is a live
  query behind every tab strip. `Document_parentId_idx` added.

## The decision: series-as-node is declined

Option (a) of §9's three: `Series` and `Project` stay as their own tables. The
sketch is closed rather than deferred a third time — the 27 Aug deferral had a
condition (`rank` gone), the condition was met, and re-reading it against the
resulting tree was the whole of what was owed.

The reasoning in one line: **the sketch's headline was paid for by other work.**
"One ordering mechanism instead of three" is what sold it, and
`repositories/ordering.ts` is container-parameterised today without it — ~240 of
its 487 lines already shared by every container kind, with ~55 lines of *move*
code and one route left doubled. What remained to buy was one *content* model,
priced at 76 files, two repositories (433 + 141 lines), eight API routes,
`seriesId` across 57 files and `projectId` across 22, plus a data migration that
must preserve ids because revisions, proposals and blob refs all point at them.

The polymorphic root array is the honest cost of declining, and
`src/lib/orderArray.ts` already absorbs it: the reader takes ids, not rows.

**If it is ever reopened, §9.2 is the finding to read first.** Folding `Series`
alone leaves the root array polymorphic across `Document` and `Project` anyway —
most of the churn, none of the headline. The trigger worth watching for is a
*third* grouping kind, which is where ~55 doubled lines stops being ~55.

## The ops layer — `production-deployment.md` §9 steps 8 and 9

Both are things the plan says must exist *before* the box is load-bearing, and
neither needs a box to write. They are `ops/`, with the runbook in
`ops/README.md` and the reasoning in that plan's new §10.

**Mechanism: systemd timers, units committed in `ops/systemd/`.** Host cron
keeps its schedule outside the repo, has no catch-up after downtime and no
failure hook — a backup missed by a reboot is silent, which is §5's whole
complaint. A scheduler sidecar wants the Docker socket, which is root on the box
that terminates TLS; a bad trade for four shell scripts. One templated unit,
`blog-job@.service`, runs `ops/<instance>.sh`, so a fifth job is a script and a
timer.

**Four jobs, not §9's two:** nightly backup (02:17 blob copy, 03:17 database),
weekly collection (Sun 04:17), monthly restore drill (first Sat 05:17).

Two properties worth carrying forward:

- **The collector's precondition is code now.** §5 says in prose that the bucket
  must be backed up before the only thing in the system that deletes bytes ever
  runs. `ops/blobs-collect.sh` refuses if the last successful offsite copy is
  missing or older than `BLOBS_SYNC_MAX_AGE_DAYS`. The copy is `rclone copy`,
  never `sync` — propagating a collector's deletion is exactly what the copy
  exists to survive, and immutable blobs make append-only free.
- **The drill restores the bucket too, and reconciles it.** It stands up its own
  Postgres and MinIO, restores the offsite blob copy into them, and fails if a
  single hash in `Blob` has no object. A `pg_dump` alone restores documents whose
  pictures are gone and reports nothing — `Revision.data` holds a valid
  `/api/blob/<hash>` to an object that does not exist. Pointing the drill at live
  R2 would pass whatever the backup contains, which is the one thing it must not
  do.

**`blob-storage.md` §11.2 is answered by a third option neither of its bullets
named.** A `profiles: ["ops"]` service in `docker-compose.prod.yml` builds the
Dockerfile's *builder* stage, which already carries `src/` and `tsx`. The runner
image gains nothing, no destructive operation lands on an HTTP surface, and
every script in `prisma/scripts/` becomes runnable in production as a side
effect — minting an agent token and rotating an AI key were **not possible at
all** before this.

## Traps learned this session

1. **`postgres:16` would have failed on the first restore.** The prod compose
   has pinned 16 since `118a5a8c`; the only data that will ever seed production
   is the development database, which runs **17.2**, and `pg_restore` 16 rejects
   a 17 archive on the header — `unsupported version (1.16) in file header`,
   before it reads a row. Verified directly with both images. Pinned to 17 in
   all three compose files: a line now, a `pg_upgrade` after the first deploy.
   The drill file must stay in step, or a drill reports a good backup as corrupt.
2. **`pg_restore --list /dev/stdin` fails on valid archives.** `did not find
   magic string in file header`, even on the matching version — naming it as a
   file makes pg_restore open it seekably. Bare stdin (`pg_restore --list <
   file`) is fine. The two spellings are one argument apart, and this was in the
   backup's *own verification step*, where the wrong one condemns every good
   backup.
3. **`docker compose exec app tar` beats naming the volume.** Compose prefixes
   volume names with the project, so a script that mounts `blog-attachments`
   works on the box it was written on and nowhere else. Reading the archive out
   through the container that already has it mounted has no such dependency.

### The next thing to do: provision the box

`production-deployment.md` §9 steps **5, 6 and 7**, in that order, and none of
them can be done from a checkout:

5. Provision the VPS, point DNS, bring the stack up, confirm TLS.
6. Create the R2 bucket and set `S3_*` in the production environment. **Before**
   the first deploy, not after: without it the app runs, serves posts, and shows
   broken images with no error naming the cause.
7. Copy the existing attachments onto the volume — 11 files, ~180KB.

Then, and only then, the ops layer becomes real: fill in `ops/ops.env`, run
`rclone config` as root, install the units, and **run `ops/restore-drill.sh`
once by hand**. Until that has passed there is no evidence any of the rest
works. `ops/README.md` has the sequence.

After that, §9's last two: verify the change feed end to end *through*
Cloudflare (the failure is silent — `archive/changes-detection.md` §6.2), and an
external uptime check against `/api/health`.

Three things to know before starting:

- The production `.env` must set `POSTGRES_USER` / `POSTGRES_PASSWORD` /
  `POSTGRES_DB`. Both the compose file and the ops scripts default them to
  `blog`/`blog`, which is a password published in this repository.
- It must also carry `APP_DOMAIN`, `NEXTAUTH_URL` and `PUBLIC_URL` — the last
  two `https://<APP_DOMAIN>`. Caddy will not start without `APP_DOMAIN`.
- `ALERT_WEBHOOK` empty means job failures are journald-only, and nobody finds
  out. That is deliberate — an unconfigured alert must not itself be a failing
  unit — and it is the one setting in `ops/ops.env` whose omission is silent.

### The one decision left — answered 31 Aug 2026: **migrate both**

**`blob-storage.md` §10.1** — whether `sketch`/`graph` SVGs move to the object
store — is decided in that plan's new §13, and the code half landed with it:
`MIGRATABLE_TYPES` gains both types, and `SketchNode` gained the data-URI prefix
guard `GraphNode` has always carried, which was the entire reason sketches were
held back.

What settled it was decoding all five distinct stored SVGs: **none references
anything outside itself** — a sketch embeds its font as a `data:font/woff2` URI
inside its own `<style>`, a graph has no style at all — and that is the property
that decides whether an inline `<svg>` may become an `<img>`. The bytes are 77
occurrences, 5 distinct, 3852 kB → 396 kB deduped, and the two *graphs* are 54%
of them in 13 occurrences, needing no code change at all.

**The migration has not been run.** It rewrites every revision in the database,
so it wants a fresh `pg_dump -Fc` first, then `--dry-run`, then a browser pass —
§13.5 has the acceptance criterion, and the specific thing to look at is a
sketch containing text: every render path strips the `<style>` today, so its
font falls back; as an `<img>` the style is scoped to the image and the embedded
font applies. Different from today is expected, wrong is not.
